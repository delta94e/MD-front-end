### Thuật ngữ
- Cửa sổ ngữ cảnh (context window): lượng văn bản/token tối đa mà mô hình "nhìn thấy" cùng lúc trong một session; càng đầy càng tốn tiền và có thể làm agent kém đi.
- Token: đơn vị nhỏ của văn bản mà mô hình xử lý và tính phí; 500k = 500.000 token.
- Nén tự động (auto-compaction / compact): khi session quá dài, harness tóm tắt lịch sử hội thoại để giải phóng context mà vẫn giữ ý chính.
- Harness: phần mềm "bọc" quanh mô hình để biến nó thành agent làm việc được (ví dụ Claude Code, Codex CLI).
- Biến môi trường (environment variable): giá trị cấu hình đặt trong shell (vd. trong `.zshrc`) mà chương trình đọc khi chạy.
- Dotfiles: các file cấu hình cá nhân bắt đầu bằng dấu chấm (`.zshrc`, `.gitconfig`...), thường được lưu trong một repo riêng.
- firstmate: công cụ của Kun — một agent "thuyền phó" mà bạn nói chuyện trực tiếp; nó điều phối nhiều agent con chạy song song.
- Crewmate (thuỷ thủ): các agent con do firstmate tạo ra để làm từng việc cụ thể.
- Điều phối (orchestrate): phân việc, theo dõi, gom kết quả từ nhiều agent.
- Hook (git hook / repo hook): script tự chạy khi có sự kiện (vd. trước commit); chạy hook lạ từ repo có thể nguy hiểm về bảo mật.
- PR (pull request): yêu cầu gộp thay đổi code vào nhánh chính, thường qua review.
- YOLO merge: merge PR luôn mà không cần người review ("you only live once").
- no-mistakes: công cụ khác của Kun — pipeline kiểm định nghiêm ngặt với review đối kháng trước khi merge.
- Review đối kháng (adversarial review): một agent cố tình tìm lỗi/chỗ yếu trong thay đổi của agent khác.
- Rào chắn an toàn (guardrails): các quy định/kiểm tra ngăn agent gây hại.
- Chính sách (policy) theo project: cấu hình trong `projects.md` quy định mỗi project được merge thế nào (YOLO, no-mistakes, cần người review).
- Artifact: trang/bản trình bày trực quan agent tạo ra để người xem duyệt kết quả.
- Prototype: bản mẫu thử nghiệm để thảo luận trước khi làm thật.

### Chỗ người mới dễ kẹt
- "Context nhiều làm agent kém đi" → mô hình phải "chú ý" đến mọi thứ trong context; càng nhiều nội dung cũ, không liên quan thì càng dễ nhiễu, quên chi tiết quan trọng, và mỗi lượt gọi càng tốn token (tiền).
- Vì sao không tự quản lý context → Kun không nói tối ưu là vô ích, mà nói chi phí chú ý của con người đắt hơn số tiền token tiết kiệm được. Giải pháp "đủ tốt": đặt một ngưỡng auto-compact rồi quên đi.
- Tên biến môi trường chính xác → caption không rõ; người học nên tra tài liệu Claude Code để biết tên đúng và cách đặt (thường là `export TÊN_BIẾN=500000` trong file cấu hình shell).
- "Ngưỡng 1M mặc định là quá cao" → để đến gần 1M token mới compact thì mỗi lượt gọi rất đắt và agent đã có thể bị suy giảm chất lượng từ lâu.
- Chuyện hook bị bỏ qua "vì bảo mật" → khi tạo môi trường làm việc từ một repo, nếu tự chạy hook có sẵn trong repo thì code lạ có thể chạy trên máy bạn. Treehouse cố ý không chạy, nhưng lỗi là không báo cho người dùng biết → sửa bằng cách cảnh báo một lần.
- Khi nào dùng YOLO / no-mistakes / người review → tiêu chí là mức rủi ro: project đồ chơi hoặc chưa release ngay → YOLO; thay đổi mà bình thường bạn sẽ nhờ người review → no-mistakes; rủi ro cao → cần chính bạn xem.
- Đưa feedback cho agent → feedback tốt là cụ thể và có tham chiếu (vd. "giống Everest và K2, hãy đi tìm ảnh"), thay vì chỉ nói "chưa đẹp".
