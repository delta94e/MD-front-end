## 🖊️ Part 1 — What is Slack Canvas (technically)?

### What the interviewer expects you to know

Canvas is Slack's **collaborative rich-text document editor** — launched 2022, embedded natively inside Slack channels and DMs.

**Think:** Google Docs inside Slack, but tightly integrated with messaging, search, mentions, and video huddles.

#### Canvas technical foundation

```
Canvas = ProseMirror (rich-text engine)
       + Custom Slack block schema
       + Operational Transform (OT) real-time sync
       + Slack URL routing scheme
       + ProseMirror key handler integration with Slack shell
```

**Why ProseMirror (not Lexical, Slate, Draft.js)?**
> *"ProseMirror is the most battle-tested rich-text foundation. Used by Atlassian, New York Times, Dropbox Paper, GitHub pull request editors. The plugin/schema extension model lets us add Slack-specific block types — @mentions, canvas-links, message references — without forking the editor engine."*

#### Custom Canvas block types (Slack schema extensions)

| Block type | What it is | Interview hook |
|---|---|---|
| `heading` (H1/H2/H3) | Auto-populates the Table of Contents panel | ToC = auto-generated by traversing the ProseMirror doc tree |
| `todo_item` | Checkbox with text (grouped in `todo_list`) | Real-time sync means two people checking the same box simultaneously → OT resolves conflict |
| `canvas_link` | Embedded reference to another canvas (preview card) | Canvas-to-canvas navigation → back button behaviour is the hard problem |
| `message_ref` | Pinned Slack message excerpt | Deep integration: canvas ≠ isolated document |
| `slack_mention` | @user, #channel, @here (inline) | Mentions in canvas → notification system integration |
| `code_block` | Syntax-highlighted code, language attribute | Keyboard shortcut conflict with Slack shell (Tab indents code vs Tab for focus) |
| `table` | Rows, columns, merged cells | Hardest block for OT: concurrent row insertion + cell edit |

## 🧩 Part 2 — Organisation: How users organise canvases

### The ambiguity

> *"Organisation was completely ambiguous when we started. We knew users had 100+ canvases and couldn't find them. We didn't know the right mental model."*

#### Five models we considered

| Model | Example product | Why it failed for Slack |
|---|---|---|
| Nested folders | Notion | Poor on mobile; cognitive overhead; most users never create folder hierarchies |
| Tags/labels | Linear | Tag combinations explode at enterprise scale (n² problem) |
| Search-first | Gmail | Fails for reference documents users rarely open but need occasionally |
| Recency list | iOS App Library | Fails for "that canvas I made 3 months ago" |
| **Channel-scoped list** | **We shipped this** | Slack is channel-centric. 89% of canvas opens came from the channel list |

#### How we made the decision

> *"We reframed the problem. 'Organisation' is not the user's goal. Their goal is: find the canvas I need when I need it, with minimum effort. Once we reframed it that way, the channel-scoped model was obvious — Slack users already orient by channel. We're not teaching a new mental model."*

**Key metric:** 89% of canvas opens came from channel-scoped list. Search covered the remaining 11%. We set a threshold: if search exceeds 30% of opens, revisit the org model.

## 🗺️ Part 3 — Navigation: Canvas ↔ the rest of Slack

### The core tension

> *"Slack has 6 primary surfaces: channels, DMs, canvas, search, video, and thread panels. Canvas is fundamentally different from the others — it's persistent and document-like. The others are ephemeral. This creates a navigation mismatch."*

#### The 6-surface navigation matrix

```
[Sidebar]──→[Channel Messages]──→[Canvas]
                 ↑                  ↕
              [DM]              [Thread Panel]
                 ↑                  ↕
              [Search]←──────[Video Huddle]
```

#### The hardest navigation decision (RFC-112)

**Problem:** When a user clicks a canvas linked in a message, then presses Back — where do they go?

- **Option A:** Back to the originating *message* in the channel
- **Option B:** Back to the *channel message list* (not a specific message)

> *"This was unresolved for weeks. We ran a prototype experiment. Dogfood result: 82% of back-button taps expected option A — the originating message. Users wanted to continue the conversation thread they came from. We shipped option A. The implementation: we store the message timestamp in the navigation history entry alongside the canvas ID."*

#### URL routing scheme

```
/archives/{channelId}                    → channel messages
/archives/{channelId}/canvas/{canvasId}  → canvas in channel
/canvas/{canvasId}                       → standalone canvas
/canvas/{canvasId}#h-{sectionId}         → canvas + section anchor (deep link)
```

**Canvas section deep linking:**
> *"Every heading block gets a stable anchor ID on creation — a slug of the heading text plus a 4-character random suffix. The anchor ID is immutable. If the user renames the heading, the display text updates but the anchor ID stays the same. Why? Because every shared URL containing that anchor would break if we generated new IDs on rename. Stable IDs are a contract with every person who ever shared that link."*

#### Keyboard shortcut conflicts (the hardest technical problem in navigation)

```
ProseMirror editor shortcuts vs Slack shell shortcuts:
  Ctrl+B  = bold text (ProseMirror)   vs  bold sidebar (Slack)
  Ctrl+K  = insert link (ProseMirror) vs  jump to DM (Slack)
  Tab     = indent code block (PM)    vs  focus next element (Slack)
  Escape  = cancel canvas edit (PM)   vs  close modal (Slack shell)
```

**Solution:**
> *"We built a focus-aware event router. Single keydown listener on the document root. If the event target is inside the canvas DOM subtree: route to ProseMirror handlers. If not: route to Slack shell handlers. Escape is special: it blurs the canvas editor and returns focus to the Slack shell — explicit focus handoff. This is why Canvas keyboard navigation feels native rather than fighting with Slack."*

#### Focus zones

Slack's three focus zones:
1. **Sidebar** (channel list, DMs, canvas list)
2. **Content panel** (canvas editor, message feed, search results)
3. **Thread panel** (right-side thread / canvas comments)

- **Tab:** cycles between zones
- **⌘+[:** shift focus left
- Screen reader: each zone has an ARIA landmark (`role="main"`, `role="navigation"`, `role="complementary"`)

## ⚡ Part 4 — Real-time collaboration (OT)

### Why Operational Transform (not CRDT)?

> *"CRDT is better for P2P and offline-first architectures. Figma uses CRDT. But Slack's architecture is server-authoritative — all operations go through our servers anyway. OT is simpler to reason about for this model, and we already had OT infrastructure from Slack messaging. Extending it to canvas was a more natural fit than introducing CRDT."*

### How OT works (explain in 60 seconds)

1. User A types "Hello" at position 0. Client applies optimistically and sends `Insert("Hello", pos=0, v=42)` to server.
2. User B simultaneously types "World" at position 0. Same process.
3. Server receives A's op first → applies it → doc now at v=43.
4. Server receives B's op (stale, at v=42). Server **transforms** B's op against A's op: `Insert("World", pos=5)` (shift by length of "Hello"). Applies. Doc now at v=44.
5. Both clients receive the broadcast and converge to "Hello World".

### Canvas-specific OT challenge we solved (RFC-98)

**Problem:** Concurrent block reorder + text edit.

- User A: drag-reorders blocks (moves block 3 before block 1)
- User B: concurrently edits text inside block 3

With position-based OT: B's edit applies to the *wrong block* after A's reorder.

**Fix:**
> *"Operations carry block IDs — stable UUIDs — not position integers. Position is computed at apply-time from block IDs. It is never transmitted. Block IDs are the stable reference. Positions are ephemeral. This was the key insight. After RFC-98: concurrent reorder + edit never corrupts documents."*

## 🔬 Part 5 — Rapid Prototyping (the unique role requirement)

### What "most experienced prototyper" means technically

> *"Experience as a prototyper compounds. Year 1: I knew WHERE things were in the codebase. Year 3: I knew HOW systems interact. Year 5: I know WHAT WON'T WORK before I build it. Now I prototype the ideas I'm genuinely uncertain about. The ideas I'm certain will fail: I kill in conversation, not in code."*

### The prototyping pipeline

```
Day 0-3:   Local Prototype  → Real codebase + real data + feature flag from day 1
Day 3-7:   Dogfood          → 8,000 Slack employees. Real usage patterns emerge.
Week 2:    1% Beta          → userId % 100 < 1 → ~350,000 users
Week 3-4:  10% Rollout      → Performance profiling in prod. Metric gates.
Sprint+1:  100% Ship        → Feature flag cleanup in same sprint.
```

### The 5 rules of good prototypes at Slack scale

1. **Real data, not mocks** — "A prototype with hardcoded text is a wireframe. It lies about edge cases."
2. **Real codebase, feature-flagged** — "Throwaway prototypes never handle the edge cases the real codebase forces."
3. **Measure early** — "We add performance markers at prototype time. A 380ms canvas-switch regression caught in prototype: 2 hours to fix. Caught after shipping to 35M: catastrophe."
4. **Share at day 3, not day 30** — record a Loom, async feedback > synchronous meeting
5. **A prototype that raises more questions than it answers is a success** — "Questions are the output, not the code."

### A prototype that changed product direction

> *"We prototyped inline comments for Canvas — like Google Docs side comments. Figma designs looked beautiful. Team was excited. My prototype took 4 days and revealed a fatal flaw: side comments required 300px right margin. On a 1280px monitor: fine. On a 1024px monitor: cramped. On mobile: comments overlapped the canvas text. Unusable. We pivoted to bottom-sheet comments before any engineering time was spent on the wrong approach. The prototype saved us 6 weeks."*

## 📐 Part 6 — Technical Lead responsibilities

### What a TL does (vs senior engineer vs EM)

| Role | Owns |
|---|---|
| **Tech Lead (me)** | Hardest ambiguous technical problems; cross-team API contracts; RFC authorship; prototype quality bar |
| **Senior Engineer** | Problems with clear technical paths; implementation quality; code review |
| **Engineering Manager** | People, career growth, delivery planning, team health |

> *"I take the problems nobody has a clear answer for yet. My team takes the problems that have a clear path. That's the division."*

### Cross-team dependencies I own

| Team | Interface I define |
|---|---|
| **Search** | Canvas block indexing API — which block types are indexed, how sections are searchable |
| **Messaging** | Canvas pin protocol in channels; share-to-message preview card format |
| **AI/ML** | Canvas summary API; auto-generated ToC; smart section suggestions |
| **Video** | Canvas co-edit during Slack huddles (focus mode spec) |
| **Mobile** | Shared canvas document schema; iOS/Android feature parity requirements |
| **Platform (Bolt SDK)** | 3rd-party app canvas block embedding API |

> *"If I'm not in design reviews with these teams: they build to their convenience. Canvas becomes fragmented. I sit in weekly syncs with Search, Messaging, Video. I write the API contract. I am the interface between Canvas and the rest of Slack's feature set."*

### RFC lifecycle (examples authored)

| RFC | Problem | Decision | Status |
|---|---|---|---|
| RFC-98 | Concurrent reorder + edit corrupted canvas | Block-ID-based OT transforms (not position-based) | ✅ Shipped |
| RFC-109 | Canvas discovery architecture | Channel-scoped list + workspace search (89% coverage) | ✅ Shipped |
| RFC-112 | Back-button after canvas-to-canvas navigation | Back → originating message (not channel root) | 🔄 In review |
| RFC-118 | Canvas full-text search integration | Index canvas block content in Search infra | 📝 Draft |

### Ambiguous problem framework

> *"When a problem is ambiguous, I don't make a decision — I make the decision surface explicit. Here are the 3 options. Here are the constraints. Here's the cheapest experiment to learn which is right. Let's run it this sprint and decide with data."*

**The 5-step process:**
1. **Reframe** — What is the user's actual goal? (Not "organise canvases" → "find the right canvas with minimum effort")
2. **Gather constraints** — mobile, enterprise scale, existing Slack mental models
3. **Prototype to learn** — not to ship. First prototype invalidates the riskiest assumption.
4. **Document with explicit trade-offs** — RFC. "We chose X. Trade-off accepted: Y."
5. **Set a metric threshold** — when to revisit. Prevents endless re-opening of closed decisions.

## ❓ Part 7 — 25 Interview Questions & Model Answers

#### Q1: What is Canvas technically?
> *"Canvas is Slack's collaborative rich-text document editor built on ProseMirror with a custom Slack block schema. Real-time sync uses Operational Transform via our collaboration service. It integrates deeply with Slack — @mentions, linked messages, channel pins, search indexing, and video huddle co-editing."*

#### Q2: Why ProseMirror over other editors?
> *"Battle-tested by Atlassian, NYT, Dropbox Paper, GitHub. The schema extension model lets us add Slack-specific node types without forking. Most other editors make extensions harder or less stable."*

#### Q3: How does OT work?
> *(Use the 5-step explanation from Part 4. Keep it 60 seconds.)*

#### Q4: Why OT over CRDT for Canvas?
> *"Slack's architecture is server-authoritative — all ops go through our servers. OT is simpler to reason about for this model. We already had OT infrastructure from messaging. CRDT would have been a larger infrastructure lift for marginal benefit."*

#### Q5: What was the hardest navigation problem?
> *"The back-button question after canvas-to-canvas navigation. Genuinely ambiguous — two reasonable options, both had defenders. We resolved it empirically: dogfood prototype, 82% of back-taps expected to return to the originating message. We shipped that."*

#### Q6: How do canvas section deep links work?
> *"Each heading block gets a stable UUID-based anchor ID on creation. Immutable — renames update the text, not the ID. URL format: /canvas/{id}#h-{anchorId}. On load: we wait for the canvas to render, then scroll to the element with matching data-anchor-id, and focus it for screen readers."*

#### Q7: How did you resolve keyboard shortcut conflicts?
> *"Single focus-aware event router on the document root. If the active element is inside the canvas DOM subtree: ProseMirror handlers get priority. Escape always blurs the canvas editor and returns focus to the Slack shell — explicit, predictable focus handoff."*

#### Q8: How do you approach ambiguous problems?
> *(Use the 5-step framework from Part 6.)*

#### Q9: What makes a good prototype at Slack's scale?
> *"Real data, real codebase, feature-flagged from day 1, performance markers from day 1, and shared at day 3 not day 30. A prototype that raises more questions than it answers is successful — questions are the output."*

#### Q10: Tell me about a prototype that changed product direction.
> *(Canvas inline comments → bottom-sheet pivot. Use the example from Part 5.)*

#### Q11: How do you manage cross-team dependencies as TL?
> *"I own the API contracts between Canvas and 6 other teams. I'm in their weekly syncs. I write the interface spec before either team builds. If I'm not there: they build to their convenience, not to Canvas's needs."*

#### Q12: What's the difference between a TL and a senior engineer?
> *"A senior engineer takes problems with a clear technical path. I take problems that don't have a clear path yet. My job is to reduce ambiguity — not to make decisions for others, but to make the decision surface explicit."*

#### Q13: How did you solve the concurrent reorder + edit bug?
> *"RFC-98. Root cause: OT operations carried positions, not block IDs. After a reorder, positions shifted and edits applied to the wrong block. Fix: operations carry stable block UUIDs. Positions are computed at apply-time. Never transmitted. That was the key insight."*

#### Q14: How does Canvas integrate with Search?
> *"We're actively working on this — RFC-118 in draft. The interface: Search team exposes an indexing API. Canvas sends block content deltas on save. Each block gets indexed with its canvas ID, section anchor, and block type. Search results link directly to the canvas section, not just the canvas root."*

#### Q15: How do you handle Canvas on mobile?
> *"Shared document schema — mobile and desktop operate on the same ProseMirror document model. The rendering layer differs. Mobile-specific constraints (touch targets, viewport) feed into the shared schema design. I define the schema constraints so mobile doesn't get surprises."*

#### Q16: What metrics do you use for Canvas navigation?
> *"Canvas-open-from-channel-list rate (target >70%), back-button success rate (landed at intended destination), canvas-to-canvas navigation depth, canvas section deep-link click-through rate. And negative metrics: navigation errors, dead-end navigations where users immediately leave."*

#### Q17: How do you decide when to revisit an architectural decision?
> *"I set a metric threshold at decision time. Channel-scoped discovery: if search > 30% of canvas opens, revisit. This prevents two failure modes: never revisiting wrong decisions, and endlessly re-opening closed decisions."*

#### Q18: What's the Table of Contents (ToC) implementation?
> *"Traverse the ProseMirror doc tree, collect heading nodes, emit {id, level, text, offset}. The ToC updates in real-time as the user types. Click a ToC entry: smooth scroll + URL hash update. The hash is the stable anchor ID, so sharing the URL takes the recipient directly to that section."*

#### Q19: How do you handle canvas performance with large documents?
> *"Virtual rendering: we only render blocks in the viewport ± 2 screens. Blocks outside this range are replaced with placeholder divs of the same height (height estimated from block type and content length). The ToC is always fully rendered since it's in a separate panel."*

#### Q20: What's the Canvas URL routing scheme?
> *(Recite the 4-line URL table from Part 3.)*

#### Q21: How do you collaborate with design as TL?
> *"I participate in every design review for Canvas. Not to design UI — to catch technical constraints early. Finding a technical impossibility in a design review costs 30 minutes. Finding it in engineering costs 3 weeks. My prototype fills the gap between Figma and reality."*

#### Q22: What does the Productivity pillar mean for Canvas?
> *"Productivity = tools that make work happen faster. Canvas sits alongside Lists, Workflow Builder, Bookmarks, Reminders. The pillar theme: reduce friction in information work. For Canvas: the org and nav experience must be fast enough that the tool never feels like the obstacle."*

#### Q23: How do you mentor engineers as TL?
> *"I take the first prototype on every new problem — my prototype sets the quality bar. I do thorough code reviews with explicit rationale, not just 'fix this'. I write RFCs that model how to think about ambiguous problems, not just the conclusion. Engineers on my team learn the framework, not just the answer."*

#### Q24: What's the hardest thing about being a TL vs an IC?
> *"The hardest thing: resisting the urge to solve the problem for the engineer. My instinct is to prototype. But if I prototype everything, the team doesn't learn the muscle. My job is to reduce ambiguity enough that the engineer can prototype confidently — then get out of the way."*

#### Q25: If you had to improve Canvas in one area, what would it be?
> *"Canvas ↔ Search integration — RFC-118. Right now, canvas content is not indexed. Users can't find content inside canvases via Slack search. For long-term retention: a document editor whose content is unsearchable will be abandoned. Search integration is the most important infrastructure investment for Canvas adoption."*
